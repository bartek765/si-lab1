Zajęcia 1: od problemu do baseline’u

4 × 45 minut pracy + przerwa po 90 minutach

Czy ten problem wymaga AI?

Przejdziesz od ręcznego rozpoznania problemu do działającego, prostego klasyfikatora regułowego.

Dlaczego zaczynamy właśnie tak?
AI nie jest domyślną odpowiedzią na każdy problem informatyczny. Zanim wybierzemy model, warto sprawdzić, czy zadanie jest wystarczająco jasno określone, czy mamy użyteczne dane, jak rozpoznamy poprawną odpowiedź oraz jakie będą skutki pomyłki. Czasem wystarczy zwykła reguła, formularz, wyszukiwarka albo zmiana procesu. W innych sytuacjach reguły szybko stają się zbyt liczne, niejednoznaczne lub kruche. Wtedy rozwiązanie uczące się z danych może mieć uzasadnienie.

Dlaczego dziś piszemy reguły samodzielnie?

Prosty klasyfikator pozwala zobaczyć cały mechanizm bez ukrywania go wewnątrz gotowego modelu: jakie informacje wchodzą do systemu, dlaczego zapada konkretna decyzja, gdzie pojawia się błąd i jak zmierzyć wynik. Taki baseline daje także punkt odniesienia. Jeżeli późniejsze rozwiązanie wykorzystujące AI nie będzie wyraźnie lepsze, bezpieczniejsze albo łatwiejsze do utrzymania, jego użycie może nie mieć sensu.

6. Zbuduj baseline v0

Uzupełnij komórkę z funkcją. Zacznij od prostego rozwiązania. Nie dodawaj wyrażeń regularnych ani skomplikowanej punktacji, dopóki wersja minimalna nie działa.

RULES = {
    "security": ["phishing", "suspicious email"],
    "account-access": ["permission", "locked account"],
    "network": ["vpn", "wi-fi"],
    "hardware": ["battery", "charger"],
    "software": ["error", "install"],
}

def classify_ticket(title: str, description: str) -> dict:
    text = f"{title} {description}".lower()
    for category, terms in RULES.items():
        if any(term in text for term in terms):
            return {"category": category,
                    "confidence": 0.7,
                    "needs_human_review": False}
    return {"category": "other",
            "confidence": 0.0,
            "needs_human_review": True}

Exit ticket, odpowiedz samodzielnie

  1. Dlaczego expected_category nie może być cechą?
    Odpowiedź: Nie wolno używać expected_category, ponieważ jest to docelowa etykieta; jej odczyt oznacza wyciek poprawnej odpowiedzi.
  2. Czym różni się test kontraktu od pomiaru jakości?
    Odpowiedź: Test kontraktu sprawdza strukturę i typ wyniku funkcji, a pomiar jakości porównuje przewidywania z etykietami (accuracy).
  3. Podaj jedną swoją regułę i przypadek, który może ją zepsuć.
    Odpowiedź: Reguła „vpn” → network może się pomylić dla „VPN authentication failed”, jeśli źródłem problemu jest zablokowane konto.
  4. Dlaczego dzisiejszy wynik na train nie wystarcza, aby uznać system za dobry?
    Odpowiedź: Wynik na train opisuje dopasowanie do znanych danych, a nie działanie na nowych zgłoszeniach; potrzebne będą validation i test.
